From a task to a merged change, with one human gate

A kit of agent skills that takes a task to a merged change: a spec when the change deserves one, evidence for every acceptance criterion, and a review before anything ships, with or without a tracker, on any VCS host.

The rules that shape the kit

A handful of decisions explain most of how the skills behave. Each one is an ADR in the repo.

  • One fixed human gate

    Spec approval is the only point where the work waits for a person. It catches a misunderstanding before it costs code. Accepting the change is not a gate: merge is an operation at draft by default, so a person merges unless you raise it.

    ADR 0013

  • One phase, one owner, one artifact

    Each phase is owned by exactly one kit skill and produces exactly one artifact. Where upstreams overlap, the kit merges them into that one owner. The slice plan lives in the spec, not in the tracker.

    ADR 0010

  • Evidence on the real app

    /aw-verify proves each acceptance criterion by driving the running app through the repo's own verify skill. A review finding counts as a defect only when a run demonstrates it; anything else is a risk.

    ADR 0011 Glossary: defect

  • Local by default, writes by access level

    Skills speak canonical operations that per-repo adapters translate. Reading is always allowed; each write operation is at write or draft, and an unconfigured repo leaves push, review requests and merges as drafts.

    ADR 0006 ADR 0007

  • Self-contained skills

    npx skills installs one folder at a time, so each skill carries what it needs: its references, its scripts, its upstream license and the rules it follows, restated in its own text.

    ADR 0002 ADR 0004

Where the skills come from

The kit draws on three upstreams and writes the rest itself. Every skill carries the aw- prefix, copies included, so it never collides with another kit's skills (ADR 0001).

Copy
An upstream skill shipped with its text unchanged except for the mechanical transform: the aw- rename, shared files moved into its folder, and references to a replaced skill pointed at the kit skill. Its upstream license sits in its folder as LICENSE.upstream.
Adaptation
A kit skill whose text derives from one or more upstream skills. NOTICE.md says what it keeps and what it changes.
Inspired
A kit skill that takes an idea from an upstream and none of its text.
Kit skill
Written from scratch for this kit, with no upstream text (ADR 0014).

Copies are pinned to a commit in upstreams.json, with the hash of every copied file in upstreams.lock.json, and scripts/sync-upstreams.mjs check fails on any edit beyond the transform. NOTICE.md lists every copy and adaptation with its upstream, pin and kind.

    Three routes, one gate

    /aw-intake sends every task down the fast, standard or epic route, and picks the longer one when in doubt. Pick a station to see what the phase does, the skill that owns it, and the artifact it leaves.

    A dashed rail marks an optional station. The full table is in ADR 0013.

    Which route?

    The questions /aw-intake asks to classify a task, in the order its rules apply them. This is a guide: /aw-intake makes the actual call, from the task and the code, and gives a reason for each.

    The rules are steps 3 and 4 of aw-intake's SKILL.md.

    Install the kit

    The README explains each route, what it writes to your repo, and how to switch Matt Pocock's plugin off where the kit is on.

    As a Claude Code plugin

    Recommended. Install with project scope in each repo that uses the workflow.

    claude plugin marketplace add samfaina/ai-workflow
claude plugin install ai-workflow@samfaina-labs --scope project

    With npx skills

    For harnesses without Claude Code's plugin system. Name a skill to install only that one.

    npx skills add samfaina/ai-workflow
    npx skills add samfaina/ai-workflow --skill aw-<name>

    Configure a repo

    Run /aw-setup once in each repo. It explores first, then interviews you one section at a time, leading each with the answer it recommends, and writes nothing until you confirm the whole set. Re-run it to change anything; it updates in place.

    What it asks

    1. Tracker: none, local markdown, GitHub, GitLab or another, and its access level.
    2. VCS: the base branch, protected branches, branch naming, commit convention, review host, merge method and access levels.
    3. Checks: a command for each check level, fast, task and full, proposed from the project's manifests and CI files.
    4. Domain docs: single-context or multi-context, and where the glossary and ADRs live.

    What it writes

    • docs/agents/tracker.md, vcs.md and checks.md, the adapters, and domain.md.
    • An ## Agent skills block pointing at all four, in AGENTS.md, or in CLAUDE.md when only that exists.
    • .aw/ in .gitignore, and on your yes, permissions.deny entries against force-push and --no-verify, and turning Matt Pocock's plugin off in the repo. It warns when Node 18 or later is missing.

    Three adapters

    tracker.md

    Where tickets live. Reads: fetch-ticket, query-tickets. Writes: publish-ticket, comment-ticket, set-status, link-tickets.

    vcs.md

    Branches, commits and the review host. Read: diff-base. Writes: start-branch, commit, push, open-review, merge.

    checks.md

    The command for each check level: run-check fast, task or full. A level with no command is reported as not run, never as passed.

    Access levels: try them

    Each write operation is at write, where the agent performs it, or at draft, where it writes the exact command or text to .aw/drafts/, tells you the path and goes on. The VCS operations below start at the unconfigured defaults. The commands are those of the GitHub VCS template, and with a review host, /aw-ship drafts open-review when push was drafted, and the merge when either was.

    Never allowed

    Whatever the access levels say, the agent never force-pushes (--force, --force-with-lease, a + refspec), never deletes a branch, local or remote, never pushes directly to a protected branch, and never passes --no-verify. These are not configurable.

    From docs/configuration.md, which also has the defaults for a repo with no configuration.

    Under another harness

    Claude Code is the reference harness. Codex, OpenCode, Cursor and the like get the skills through the SKILL.md standard, and npx skills installs them where Claude Code's plugin system is missing. Install aw-build, aw-verify and aw-review with their phase procedures, and aw-converge and aw-implement with all four. The verify skill lives in .claude/skills/ whatever the harness. permissions.deny is Claude Code's alone, and /aw-converge and /aw-implement refuse to start where the harness cannot start subagents.

    What the kit writes in a repo. Pick a node to see which skill writes it and whether it is committed.

      Anatomy of a spec

      A spec is a living document in the repo, at docs/specs/<slug>/spec.md, versioned with the code it describes (ADR 0003). Move this example through its statuses to see what each phase changes.

      ---
      status: draft
      ticket: LIB-42
      ---

      # Renew a loan

      ## Problem and goal

      A member can renew a loan only at the desk. Once this ships, they renew it from their loans page.

      ## Acceptance criteria

      • AC-1: Given a loan with no hold on its book, when the member renews it, then its due date moves 14 days later.
      • AC-2: Given a loan whose book another member holds, when the member renews it, then the renewal is refused and the due date stays the same.
      • AC-3: Given a loan renewed twice, when the member renews it again, then the renewal is refused with "renewal limit reached".

      ## Out of scope

      • Renewing at the desk, which stays as it is.

      ## Boundaries

      ### Always
      • Run the task checks before each commit.
      ### Ask first
      • A change to the loans table's schema.
      ### Never
      • Touch the payments module.

      ## Design

      A renew operation on the loans service, called by a button on the loans page.

      ## Slice plan

      Written by /aw-slices after spec approval.

      1. [ ] Renew a loan with no hold (AC-1). AFK.
      2. [ ] Refuse a held or twice-renewed loan (AC-2, AC-3). AFK.
      1. [x] Renew a loan with no hold (AC-1). AFK.
      2. [x] Refuse a held or twice-renewed loan (AC-2, AC-3). AFK.

      ## Test strategy

      Proposed: the loans service's renew, the highest seam that reaches the behaviour.

      Agreed: the loans service's renew, which catches the renewal rules and misses the button on the loans page.

      ## Traceability

      CriterionEvidence
      AC-1test: tests/renew.test.tstest: tests/renew.test.ts; verify: docs/specs/renew-loan/verify/ac-1.md (passed)
      AC-2test: tests/renew.test.tstest: tests/renew.test.ts; verify: docs/specs/renew-loan/verify/ac-2.md (passed)
      AC-3test: tests/renew.test.tstest: tests/renew.test.ts; verify: docs/specs/renew-loan/verify/ac-3.md (passed)

      ## Open questions

      BLOCKS: Is the renewal period 14 days for every kind of book?

      RESOLVED: 14 days for every kind of book.

      Frontmatter
      status moves from draft to approved at spec approval, and to implemented when /aw-ship ships it. A spec a later one replaces becomes superseded.
      Acceptance criteria
      Numbered AC-n, each a verifiable Given, when, then with an observable result. Everything after them points back at these numbers.
      Boundaries
      What the agent always does, asks first about, and never touches during this change.
      Slice plan and Test strategy
      /aw-slices writes them after approval: vertical slices, each covering at least one criterion and marked AFK or HITL, and the seams agreed with you. /aw-build ticks each done marker.
      Traceability
      One row per criterion with its evidence. At draft it holds the planned evidence, whose paths need not exist yet; /aw-build points each row at the tests that landed, and /aw-verify adds its verify: result.
      Open questions
      A BLOCKS: item must be resolved before approval; the spec check fails on one from approved on.

      The template is SPEC-TEMPLATE.md, and aw-check-spec checks every spec against it with a script.

      Implementation and convergence runs

      Two commands run several phases in one call. Each phase still runs through its own phase procedure, so it keeps its one owner. Neither ever pushes, opens a review request or merges: shipping stays with /aw-ship.

      /aw-implement

      Takes an approved spec with a slice plan, or a fast-route task, from what is left to build to a review with no introduced defect. It builds each AFK slice in a subagent of its own, in series, and each HITL slice in the main session; verifies in a subagent; reviews in the main session; and runs the rounds of a convergence run when that review holds an introduced defect.

      It asks only during a HITL slice or to agree a test seam. It refuses to start with no subagents, with commit at draft, with uncommitted changes, or with a spec that is not approved. When it stops, it says why, and running it again resumes from the first slice not done. Its journal is .aw/implement/<slug>.md.

      ADR 0017

      /aw-converge

      Takes a work branch from a review report with introduced defects to one with none. Each round is a fix run, /aw-verify when the fix calls for it, and /aw-review. The fix run and the verify run each get a subagent; the review runs in the main session, which has not seen how the defect was fixed.

      It stops when the latest review holds no introduced defect, at its limit of three rounds, which a call can raise, as in /aw-converge 5, or on anything a round cannot resolve. A repo cannot change the limit, and running it again starts a new count.

      ADR 0016
      1. build each slice
      2. verify
      3. review
      4. rounds (only with introduced defects)
      5. stop: clean, limit or reason

      Questions adopters ask

      Do I need a tracker?

      No. With no tracker the task arrives as free text and every tracker write leaves a draft. Only /aw-wayfinder needs one, and it offers to create a local-markdown tracker. Defaults when unconfigured

      Will the agent push or merge on its own?

      Not unless you raise those operations to write. Even then, it merges only when the review found no proven defect and the full check level passed, and for a change with a spec, once the spec is implemented. ADR 0013

      Does every task need a spec?

      No. The fast route has no spec and no gate: /aw-intake states 1 to 3 done-when criteria instead. A task that changes a contract, stored data or security, or contradicts a spec, takes the standard route. aw-intake

      What if my repo has no verify skill?

      Then every acceptance criterion needs test: or manual: evidence. /aw-create-verify writes one for the repo's app. ADR 0011

      Does the kit install hooks?

      No, neither agent hooks nor git hooks. /aw-setup only offers permissions.deny entries, and a mechanical control is added only when /aw-retro finds an error class that happened twice. ADR 0009

      Can I keep Matt Pocock's plugin installed?

      Yes: keep it at user scope and turn it off in the repos that use the kit, so the two never offer competing skills for the same phase. README

      What happens without Node?

      aw-check-spec walks the same checklist by reading and marks the result as not script-verified, never as passed. /aw-setup warns up front. ADR 0012

      Is the review posted to the pull request?

      No. The review report stays local, under .aw/, and is never posted to the review host. Glossary: review report

      Is there a compatibility promise?

      No, not before 1.0. The kit is built for its author's own use and published as is; anyone can use it or fork it. ADR 0005

      Maintaining the kit

      For whoever changes the kit itself. The scripts are dependency-free Node 18+, run as node <path> (ADR 0008).

      • Checks. node --test runs the tests and node scripts/validate-kit.mjs the kit invariants. CI runs both on every pull request.
      • Upstream copies. node scripts/sync-upstreams.mjs install writes the copies at their pins, check verifies them offline, and report lists what changed upstream since each pin.
      • This page. validate-kit fails when site/skills.json misses a skill, names one the plugin does not list, or disagrees with NOTICE.md or a skill's frontmatter.
      • Changing a rule. Skills restate rules word for word, and so does this page: git grep a rule's wording under skills/ and site/, and change every copy in the same diff. .claude/CLAUDE.md
      • Releases. A semver tag vX.Y.Z, the same version in .claude-plugin/plugin.json and the marketplace entry, and a hand-written changelog entry. Without the version bump, installed plugin users never see the update. ADR 0015

      The README lists every invariant the validator checks.
